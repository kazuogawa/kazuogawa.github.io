# Portfolio Loop Triage

## 前提確認

1. 同じrun内で `$loop-constraints` と `$loop-budget` が完了していることを確認する。
2. `.github/PORTFOLIO_REVIEW_GUIDELINES.md` を最後まで読む。
3. `STATE.md` と直近24〜48時間のgit履歴を確認する。
4. 必須ファイル不足、kill switch有効、または予算ガードによる停止時は終了する。

## 証拠収集

1. `make check` を実行する。
2. `make build` を実行する。
3. ビルド警告を確認し、次の要件が保持されていることを確認する。
   - `<html lang="ja">`
   - description、canonical、OG、Twitter Card、Person JSON-LD
   - Google Analytics `G-HR4K43KTKS` とAstroの `is:inline`
   - `public/images/` の参照画像
4. ブラウザを利用できる場合は、レビュー基準に指定されたPC・スマホviewport、ライト・ダーク、ナビゲーション、メニュー操作、問い合わせ導線を確認する。
5. ネットワークを利用できる場合のみ `make audit` と外部リンクの死活確認を行う。実行できない項目は成功扱いにせず、未確認として記録する。
6. ドキュメントドリフトを確認する。
   - `AGENTS.md`、`README.md`、`LOOP.md`、`docs/`、`.agents/skills/` に記載された構成、開発コマンド、権限境界、参照パスを実ファイル、`package.json`、`Makefile`、関連設定と照合する。
   - 不存在の参照、実装と異なるコマンド、重複・矛盾する拘束ルールを証拠付きで記録する。
   - 全文書の言い換えや表記統一は行わず、実行結果または権限判断に影響するdriftを優先する。
7. リファクタリング候補を確認する。
   - 直近24〜48時間の変更を起点に、重複、責務過多、不要な分岐・状態・変換、既存規約からの逸脱を静的な証拠で確認する。直近変更がない場合は週1回だけリポジトリ全体を確認する。
   - 提案には影響、具体的な根拠、対象ファイル、最小変更方針、検証方法を含める。
   - 好みだけの提案、全面的な書き換え、計測できない抽象的な「クリーンアップ」はfindingにしない。

8. 次の手順で、モデル更新に伴うスキル棚卸しを行う。

## モデル更新に伴うスキル棚卸し

目的は、新モデルが追加指示なしでこなせるようになった作業を見つけ、価値を失ったスキルの削除・縮小を提案すること。参照回数や未使用期間による整理ではない。

1. 実行環境から確認できたモデルID・reasoning effortと、利用可能なスキルの名前・提供元・版または内容hashを、`STATE.md` の前回記録と比較する。初回、モデル・設定・スキル構成の変更時、人間からの再評価指示時に見直す。同条件の再評価は新しい証拠がある場合だけ行い、未検証項目は保持する。モデルを特定できない場合は推測せず未確認と記録する。
2. リポジトリ内、個人用、プラグイン提供（superpowers・ponytail等）を対象にする。セッションのスキル一覧とそこに示された保存先・提供元を起点に、必要な本文・参照・同梱資産を読む。一覧にないものや読めないものは確認範囲外と明示し、全インストール済みスキルを確認した扱いにしない。ホーム全体や認証情報は探索しない。
3. 一般的な推論・計画・実装手順の補助と、固有の業務知識・ユーザーの好み・安全制約・ツール手順・スクリプト・テンプレートを区別する。前者の過剰な手順、不要な承認待ち、広すぎる発動条件を比較候補とする。後者をモデル能力で代替できると推測しない。提供元やモデル名だけで不要と判定しない。
4. 比較候補ごとに、通常ケースと失敗しやすいケースの代表課題、品質・指示遵守の合格条件を先に決める。同じ対象モデル・reasoning effort・入力・ツール・予算で、対象スキルあり／なしの独立した新規コンテキストの実行記録を比較する。なし側に対象スキルの本文・要約・あり側の回答を渡さず、他の指示は揃える。自動読み込みや親会話の継承を除外できない場合は有効な比較としない。既存の比較記録を使う場合も条件とスキル版の一致を確認する。
5. 品質、ルール違反、手戻り・確認待ち、取得できるtoken数・所要時間を記録する。計測不能な値は未確認とし、一度の成功やモデルの宣伝・自己評価だけで削除可能と断定しない。対象外のモデルや他プロジェクトへ結論を一般化しない。
6. 次のいずれかとして報告する。
   - **削除候補**: 両課題でスキルなしでも合格し、品質・指示遵守が劣化せず、作業量が同等以下。失われる固有情報・資産・他スキルからの依存がないことも確認できた。
   - **縮小候補**: 一般的な補助は不要でも固有情報・資産が残る。削る部分と残す部分を具体的に示す。
   - **維持**: スキルによる改善、または引き続き必要な固有の役割がある。
   - **未検証**: 比較記録、対象モデルへのアクセス、コンテキスト分離、他用途への影響などの証拠が不足している。次に試す課題と不足条件を示す。
7. 比較は現在レベルの読み取り専用権限・残予算・サブエージェント上限内で行う。制約を緩めず実行できない比較は未検証として別途検証を提案する。L1ではサブエージェントを使わず、L2・L3でも後続maker/checkerに必要な枠を消費しない。スキル内に書かれた外部送信・編集・インストールを棚卸しの権限と解釈しない。

削除候補には対象モデル、スキル名・提供元・版、代表課題と両条件の結果・実行記録参照、失われる機能と他用途への影響、削除対象の単位を添える。プラグイン内の1スキルの評価をプラグイン全体の不要判定にしない。

評価の参考: [モデル更新時のスキル見直し](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)、[スキルの評価方法](https://developers.openai.com/blog/eval-skills)。

## STATE更新

`STATE.md` の `Loop Control` は変更せず、次のフィールドとセクションだけを更新する。

- `Last run` フィールド: 日時、パターン、レベル、結果
- `High Priority`: 今日対応すべき失敗、または人間判断
- `Watch List`: 低優先度または未確認項目
- `Recent Noise`: 問題なしと確認できた項目
- `Post-Run Critique`: 検証上の不足と次回の具体的な改善

各findingには影響、証拠または再現条件、判明している対象ファイル、推奨する次の行動を含め、簡潔に記述する。

ドキュメントドリフト、リファクタリング提案、スキル棚卸しの削除・縮小候補と未検証項目は原則Watch Listへ記録する。実行不能、安全性、拘束ルールの矛盾、または具体的な不具合に直結し、人間判断が必要な場合だけHigh Priorityへ記録する。問題がなければ確認範囲をRecent Noiseへ記録する。

スキル棚卸しの日時・モデル・reasoning effort・確認したスキル構成と維持判定はRecent Noiseに簡潔に残し、次回の比較用に保持する。候補と未検証項目は同じ所見を重複登録せず更新する。個人用・プラグインの非公開本文やローカルのユーザー名を含む絶対パスを、git管理されるSTATEやログへ転載しない。

操作範囲と後続の修正対象は [LOOP.md](../../../LOOP.md) のreport-only規定・allowlist、ツール権限は [docs/safety.md](../../../docs/safety.md) に従う。

現在レベルのrunbookに後続フェーズがない場合だけ、最後に `$loop-budget` を再実行してrun-logへ記録する。後続フェーズがある場合は、そのrunbookの終了時に1件だけ記録する。
